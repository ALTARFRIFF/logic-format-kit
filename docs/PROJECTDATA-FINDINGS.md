# `ProjectData` 内部结构：已实证结论

数据来源：`_P1`（1 轨，130,647 B）、`_TRK1`（2 轨，132,937 B）、`_TRK2`（3 轨，135,225 B）。
三个文件**同一条血脉**，每次只加一条音频轨。

---

## 1. 文件 = 24 字节头 + 平铺的块流

```
[24B 文件头]  23 47 c0 ab d1 09 XX 00 …      XX = 对象类型（03 = Song）
[gnoS] Song
[qeSM] …
[karT]/[nCuA]/[OCuA]/[UCuA]/[ivnE]/[qSvE]/[qeSM] …
```

每块：`tag(4)` + 24 字节头 + **`u32 LE 长度 @+28`** + 载荷，**块总长 = 长度 + 36**。

**遍历规则对全部三个文件成立，都恰好走到文件末尾，零失配**：

| 文件 | 大小 | 块数 | 遍历终点 |
|---|---|---|---|
| `_P1` | 130,647 | 444 | 130,647 (+0) |
| `_TRK1` | 132,937 | 453 | 132,937 (+0) |
| `_TRK2` | 135,225 | 462 | 135,225 (+0) |

> 注意：`karT` 的长度可以是 **0**，表示「我不含载荷」。这不破坏遍历——因为块总长仍是 36。

## 2. 对象 ID = 序号左移 18 位（关键突破）

`_TRK2` 里 16 个 `karT(0)` 只有 **1 个字节**不同，位置 `+10`：

```
+8 的 u32: 00 00 00 00 → 04 00 00 00 → 08 00 00 00 → 0c → 10 → 14 → 18 → 1c → 20 …
                     = 1<<18      = 2<<18      =3<<18 …
         以及 0xe4 << 18
```

**所以对象 ID 不是随机 UUID，而是 `index << 18`，顺序递增。**

这条把「从零建轨」从「猜字节」变成了「分配号 + 写引用」。

`karT(58)`、`ivnE(471)` 的 `+10` 同样是这个 ID 的第三个字节；`ivnE` 的 `+52` 是同一个 ID 的第二份拷贝。

## 4. `gnoS` 每轨 +80 字节，分散在 4 处

```
+7580   24 B   14 00 00 00 | 60 00 00 00 | <16B ID>
+7820   24 B   17 00 00 00 | 20 00 00 00 | 00*16
+16704  16 B   <4B> 14 00 00 00 | 60 00 00 00 | <4B ID>
+16864  16 B   <4B> 17 00 00 00 | 20 00 00 00 | <4B ID>
```

`0x14`=20、`0x60`=96、`0x17`=23、`0x20`=32 这些值在 `karT(58)` 里也出现过，说明 Song 里存的是**同一条轨在四张不同表里的记录**。

## 7. 对实现的含义

不需要「猜格式」，可以按这个流程做：

1. `index = max(现有 ID) >> 18 + 1`
2. 复制常量块（`OCuA(237)` / `UCuA(303)` / `UCuA(348)`）
3. 复制模板块（取本工程最后一条音频轨的 `nCuA` / `ivnE` / `karT(58)` / `qSvE` / `karT(0)` / `qSvE(16)` / `qeSM(309)`），把其中**所有 `index<<18` 形式的 4 字节**替换成新号，再生成新 UUID
4. 在 6 个插入点插入、在 `gnoS` 的 4 处插入
5. 修 3 处长度：被改块的 `+28`、文件头 `+16` 的总长

**验收方式**：程序复现 `_TRK1`→`_TRK2`，与真 `_TRK2` 逐字节比（掩掉 UUID 与时间戳）。这比「让 Logic 静默打不开」好调试得多。

### 9.2 `gnoS` 的 +80 字节 = 两张对象登记表各插一条 + 两处 16 字节

插入的两条 24 字节登记项，形状 `u32 类型码 | u32 长度 | 16 字节 UUID`：

```
14 00 00 00 | 5c 00 00 00 | 02 1a cd 32 cb c0 11 f1 81 1f 63 cd bd 36 65 96
17 00 00 00 | 1c 00 00 00 | 02 1a fb 18 cb c0 11 f1 bc 01 8c 08 9a 7f f3 59
```

类型码 `0x14`=20、`0x17`=23；第二字段是该对象的载荷长度（92 / 28）。
另有两处 +16 字节的引用（`cb f1 01` 前缀 = 「指向登记项」的反向索引）。

**这是唯一还没解的部分**：`gnoS` 内部这套登记/索引表的语义。
其余 9 处增量都是「复制常量块 + 改对象 ID（`+8 = 序号<<18`）+ 改名字字符串」。

### 9.3 已验证可安全复用的常量（另见 9.4–9.5 更正）

* 音频轨通道条三块 `OCuA(237)` / `UCuA(303)` / `UCuA(348)` —— 两次新增逐字节相同
* `karT(0)` 容器块 36 字节 —— 常量
* `karT(58)` 块 —— 只有 `+8` 对象 ID 与 `+44` 递增字段变化
* 对象 ID = `序号 << 18`，顺序分配（不是随机 UUID）

### 9.4 更正：`karT` 顶层只有 4 个容器，不是「每轨一个」

`find_tracks()` 按「`karT` 长度 0」分组会得到 4 个巨大的容器块（轨道表 / 混音器 / 环境 / 尾部），
**不是** 54 条轨道。真正的「一条音频轨」定位方式是下面这个。

### 9.5 音频轨的通道条 = 996 字节，位于混音器容器内

`[OCuA(237)] [UCuA(303)] [UCuA(348)]` 三块相邻，共 `3×36 + 237+303+348 = 996` 字节。

| 文件 | 组数 | 名字 |
|---|---|---|
| `_P1` | 1 | Audio 1 |
| `_TRK1` | 2 | Audio 1, Audio 2 |
| `_TRK2` | 3 | Audio 1, Audio 2, Audio 3 |

载荷内偏移：`+36..+273`（OCuA）、`+309..+612`（UCuA 303）、`+648..+996`（UCuA 348）。
名字在 `OCuA` 载荷里（内嵌一个 `NSKeyedArchiver` bplist）。

**关键实测：`_P1` 的 Audio 1 与 `_TRK1` 的 Audio 1 两块 996 字节完全相同（0 处差异）。**

→ 一条默认音频轨的通道条是**常量模板**。这意味着：
* 新增一轨 = 复制这 996 字节 + 改名字 + 改对象 ID + 修 4 张表
* 推子 / pan / mute / solo / Send / 输出路由 **都在这 996 字节里**，
  用「同一文件内多条轨迹各自只改一个变量」的阶梯一次性全解出来

### 9.6 通道条内部只有 4 类可变字节（Audio 1 vs Audio 2 实测，44 处差异）

两条**都是默认状态**的音频轨，996 字节里只有这些不同：

| 偏移 | 内容 | 说明 |
|---|---|---|
| `+14` | `00`→`01` | OCuA 块头 **+14 的轨道序号** |
| `+42` | `00`→`01` | OCuA 载荷 +6 的轨道序号（与 `.cst` 的双槽位同构）|
| `+103` | `31`→`32` | 名字里的那一位（"Audio **1**" → "Audio **2**"）|
| `+225` | 16 字节 | UUID #1（OCuA 载荷尾部）|
| `+287` | `00`→`01` | UCuA(303) 块头 **+14 的序号** |
| `+596` | 16 字节 | UUID #2（UCuA 303 载荷尾部）|
| `+626` | `00`→`01` | UCuA(348) 块头 +14 的序号 |
| `+980` | 16 字节 | UUID #3（UCuA 348 载荷尾部）|

结论：**一条默认音频轨的通道条 = 996 字节常量 + 3 个序号字节 + 名字 + 3 个 UUID。**
新增音频轨的通道条因此可以 100% 确定地合成。

推子/pan/mute/solo/Send/输出路由必然也在这 996 字节里（两条都是默认值所以看不出），
需要一份「一条轨只改一个变量」的阶梯工程才能逐一定位。

## 十、`_MIX-A.logicx`：推子 / pan / 输出 / 静音的字节位置（实测）

文件 136,430 B / 518 块。会话里新建了 9 条音频轨，每条只改一个变量。
`OCuA(201)` 是编曲区轨头（273 个），`OCuA(237)` 才是混音器通道条（7 个）。

**基准取 `_TRK1` 的 Audio 2（真正未改过的默认条）**，把「名字 / 序号 / 3 个 UUID」这批
固定噪声偏移掩掉后，残差只剩下面几处：

| 偏移 | 默认 | 改动 | 判定 |
|---|---|---|---|
| **`+121`** | `0x5a`=90 | Audio 2（音量 −20 dB）→ `0x1c`=28 | **音量**（u8 推子位置，90 ≈ 0 dB）|
| **`+125`** | `0x40`=64 | Audio 3（pan 最左）→ `0x00`；Audio 4（pan 最右）→ `0x7f` | **pan**（u8 0–127，64 = 居中）|
| **`+126`** | `0x00` | 所有改过的条 → `0x02`；**Audio 5（mute）→ `0x03`** | **标志字节**，bit0 = mute，bit1 = 「非默认」|
| **`+128`** | `0x00` | Audio 8（输出 Bus 5）→ `0x06` | **输出目的地**（0 = Stereo Out）|

### 未定位

### `ivnE(471)` 已排除

残差只有**名字、序号（+166/+168/+171）、UUID**，**不含任何音量/pan 数据**。

## 十一、`_SOLO-A.logicx`：独奏位定位（`_MIX-A` → `_SOLO-A` 逐轨对比）

两个工程同为 12 条音频轨，唯一差别是独奏状态（Audio 3 / Audio 7 独奏，Audio 6 取消）
外加用户顺手取消了 Audio 5 的静音。逐轨比通道条，掩掉名字/序号/UUID 噪声后：

| 轨 | 变化 | 结论 |
|---|---|---|
| Audio 3（新独奏） | `+124: 00→01`、`+126: 02→00` | `+124` bit0 = 独奏 |
| Audio 7（新独奏） | `+124: 00→01`、`+126: 02→00` | 同上，**两个独奏可共存** |
| Audio 6（取消独奏） | `+124: 01→00`、`+126: 00→02` | 反向验证 |
| Audio 5（取消静音） | `+126: 03→02` | **`+126` bit0 = 静音**，第二次独立确认 |
| 其余 8 条 | 0 处差异 | 独奏不影响其他轨任何字节 |

`+124` / `+126` 都是 **`OCuA` 载荷 +88 / +90**（对 237 字节的 201 块和 996 字节的 237 块同样成立）。

* `+124` bit0 = **独奏**（1 = 开）
* `+126` bit0 = **静音**（1 = 开）
* `+126` bit1 = 「通道条偏离默认」；但**独奏时会被清零**，语义未定，
  写入时先只动 bit0，bit1 保持原样

### 独奏不写静音
Audio 6 独奏时，其余 8 条轨的 `+126` bit0 全为 0 → Logic **不**把「独奏导致别人静音」写进文件。

### Audio 7 = 带 Send 的轨，通道条 1108 字节
`OCuA(201 或 237)` + **三个** `UCuA`（普通轨只有两个）。多出来的那个 `UCuA` 就是 Send。

## 十二、推子 dB 曲线（`_FADER.logicx` 十点标定，全部命中）

音量字节在 **`OCuA` 载荷 +85**（`OCuA(201)` 与 `OCuA(237)` 都成立）。

| 轨 | 设定 | 字节 |
|---|---|---|
| Audio 1 | 0 dB | `0x5a` = 90 |
| Audio 2 | +6 dB | `0x7f` = 127 |
| Audio 3 | −3 dB | `0x4b` = 75 |
| Audio 4 | −6 dB | `0x3f` = 63 |
| Audio 5 | −12 dB | `0x2d` = 45 |
| Audio 6 | −20 dB | `0x1c` = 28 |
| Audio 7 | −30 dB | `0x10` = 16 |
| Audio 8 | −40 dB | `0x09` = 9 |
| Audio 9 | −60 dB | `0x02` = 2 |
| Audio 10 | −∞ | `0x00` = 0 |

**规律（十点零例外）**
```
byte = clamp( int(90 * 10 ** (dB / 40)), 0, 127 )      # dB = -inf 时 byte = 0
```
验算：−3→75.71→75、−6→63.72→63、−12→45.00→45、−20→28.46→28、−30→16.02→16、
−40→9.00→9、−60→2.85→2、+6→127.10→127。**取整是向下取整（int 截断），不是四舍五入。**

反解：`dB = 40 * log10(byte / 90)`。注意 −40 dB 以下一格约 3 dB、−60 附近一格约 8 dB，
所以低端读数只能精确到格。`0` 表示 −∞。

## 十三、Send 记录 = `UCuA(76)`（`_SEND.logicx`，15 条样本）

Send **不在**通道条 `OCuA` 里，每条 Send 是一个独立的 **`UCuA(76)`** 对象，排在该轨的
`OCuA` 之后、通道条 `UCuA(303)/UCuA(348)` 之前。

| 偏移 | 含义 | 证据 |
|---|---|---|
| **`+16`** | `01` = Post，`00` = 另一种（唯一一条 Pre 样本） | 15 条里 14 条为 `01` |
| **`+17`** | **电平字节，与推子同一套 0..127 律** | `5a`/`3f`/`2d`/`1c`/`10`/`09`/`02`/`00` 八种值，正好对上 0/−6/−12/−20/−30/−40/−60/−∞ |
| **`+20`** | **目的地 = bus 号 + 3** | Bus 3→`06`（多条）、Bus 5→`08`、Bus 7→`0a` |
| `+27` | 电平镜像（末字节同样等于 +17） | 15 条全部相同 |
| `+60`..`+75` | 16 字节 UUID | 每条不同 |

`+17` 与 `+27` 都等于电平字节；`+24..+27` 是 4 字节窗口，**只写 +27 一个字节**，
不要动 `+24..+26`（它们是随机 ID 片段，十点里只有全 0 的那个轨是 0）。

未定：唯一那条 Pre 样本 `+20` 是 `01`，不符合 `bus+3`，所以 **Pre/Post 的写法定性还需一条样本**。
现实现只写 Post。

结论：它们**不是**「每次保存自增的累加器」，而是**内容派生值**——只在轨道数变化时才改，
所以必须精确复刻，不能任意填。这也解释了为什么我的实现（随机/自造基数）会被 Logic 拒绝。

推论（下一步的搜索方向）：它们是「随轨道数变化、且与保存无关」的派生值，
最可能是**该表各记录的某种序号/时间戳基值**，应按 `_TRK1 → _TRK2` 的增量（不是绝对值）反推。
注意：两张表的起点在 `_TRK1`(16324) 与 `_TRK2`(16372) 之间差了 48，所以**不能按绝对偏移比较**，
必须先按 `(code, rec)` 定位表头再按记录下标取字段。

## 十五、三档样本（3/4/5 轨）对照：ID 字段规律 + 一个反转性发现

样本：`_TRK2`(3 轨) / `_TRK3`(4 轨) / `_TRK4`(5 轨，用户新建空工程)。

### 15.1 `karT:58` 的数量与 `+8`
| 文件 | 轨数 n | karT:58 数 | `+8` 序列（u32） |
|---|---|---|---|
| `_TRK2` | 3 | 13 | 0, 88,92,96, 80,88,92,96, 72,76,80,84, 0 |
| `_TRK3` | 4 | 15 | 0, 88,92,96,100, 80,88,92,96,100, 72,76,80,84, 0 |
| `_TRK4` | 5 | 17 | 0, 88,92,96,100,104, 80,88,92,96,100,104, 72,76,80,84, 0 |

- **数量 = 2n + 7**（13 / 15 / 17 全部吻合）
- **`+8` = 72 + 4i**，i 是该对象在通道序里的位置；三个分组分别是
  第 1 组 = n 个（从 88 起）、第 2 组 = n+1 个（从 80 起）、第 3 组恒 4 个（72..84）、末尾 1 个 0。

### 15.2 `ivnE:471` 的 `+16`
| 文件 | `+16` 序列 |
|---|---|
| `_TRK2` | Preview 72, Audio1 88, Audio2 92, Audio3 96 |
| `_TRK3` | 72, 88, 92, 96, 100 |
| `_TRK4` | 72, 88, 92, 96, 100, 104 |
规律：`Preview = 72`，`Audio k = 84 + 4k`（k 从 1 起）。

### 15.3 通道条 `OCuA` 的三个字段
- `+8` 恒为 **0x12350000**（三档样本、所有音频条完全一致）→ 是**类型码，不是对象 ID**。
  之前「新条写成 257<<18」的判断是误读，`+8` 根本不该被改。
- `+6` = 通道序号 0..n-1
- `+67` = 49 + 序号
- `+4` = 0x40（音频）/ 0x43（乐器）

### 15.4 反转性发现：行头是**预分配**的，不缺
`_TRK3`（Logic 显示 4 条轨）里 `OCuA` 长度分布是 `201×271 / 14×13 / 237×5`，而**长度为 201 的对象里已经存在名为 Audio 5 / Audio 6 / Audio 7 的行头**（`+6` = 4,5,6，`+4` = 0x40）。

`_TRK4`（5 轨）同样：显示 5 条轨，但 201 行头里有 Audio 1–4 与 Audio 6–8。

**结论：编曲区行头是预先分配、且数量远多于实际轨数的。新轨不出现不是「缺行头」，而是某个我们还没找到的「轨道总数」在限制它。** 这也解释了为什么把 `gnoS` 整块换成真实值（`_F1`）仍然只显示 3 条轨。

### 15.5 目前仍然缺的那一项
一个**轨道计数**字段。三个样本里唯一随 n 单调且未被我复现的量尚未定位；
已知并已复现的计数候选（`gnoS@94` +4、`qSvE` 80 字节块数、`nCuA` +4、`karT:58` 2n+7、`ivnE:471` 个数）**都已正确写入**，故计数不在这批里。
下一步应比对 `OCuA:201` 行头里「已用 / 未用」的区分字节（同一文件内 Audio 1–4 与 Audio 5–7 的差异），那里最可能藏着「哪些行是真轨」。

### 15.6 重要负结果：`_D14` 与真实 `_TRK3` 已无「语义字节」差异

修正 UUID 掩码判据（只要 `byte[6] & 0xF0 == 0x10` 且 `byte[8] & 0xC0 == 0x80`，**不再检查 byte[9]**）后重算：

| 项 | 结果 |
|---|---|
| UUID 字段数 | 真 177 / 我 177（**完全相等**） |
| 非 UUID 差异 | **122 字节** = `gnoS` 90 + `qeSM` 32 |
| `qeSM` 那 32 字节 | `+8/+9`，已证明是每次保存重生成的随机 ID |
| `gnoS` 那 90 字节 | 逐段检查后**全部是 UUID 尾部碎片**（15 段 × 6 字节），其 `byte[8] = 0xf1` 所以没被判据覆盖 |

**结论：`_D14`（我生成）与 `_TRK3`（真实 4 轨）在结构、计数、索引、UUID 数量上已经完全一致，且不存在任何非标识符的字节差异。** 但 Logic 对两者的处理不同（4 轨 vs 3 轨）。

由此可以排除「漏写了某个计数器」这一类解释；剩下的唯一可能是 **UUID 的取值本身必须配对** ——即新轨在 `gnoS` 里被某条记录以某个 UUID 引用，而通道条/`ivnE` 必须使用**同一个值**。真实文件里这些位置互相相等，我的生成器却各自随机（唯一但不相符）。

## 二十一、`qeSM:309`（`*Automation`）里那几个字节：**有规律，可计算**

同一份文件内，把每条音频轨自己的 `*Automation` 序列排出来（`_TRK3` 4 轨 / `_TRK4` 5 轨）：

| 文件 | 序号 | id | `@234` | `@242` | `@300-301`（u16 LE） |
|---|---|---|---|---|---|
| `_TRK3` | 0 | 12 | 80 | 249 | 436 |
| | 1 | 13 | 88 | 255 | 436 |
| | 2 | 14 | 92 | 254 | 436 |
| | 3 | 15 | 96 | 253 | 436 |
| | 4 | **46** | **100** | **252** | **117** |
| `_TRK4` | 0 | 8 | 80 | 248 | 442 |
| | 1 | 38 | 88 | 255 | 442 |
| | 2 | 11 | 92 | 254 | 442 |
| | 3 | 4 | 96 | 253 | 442 |
| | 4 | 5 | 100 | 252 | 442 |
| | 5 | 39 | **104** | **251** | **442** |

### 21.1 三条规律
1. **`@234` = 该自动化序列在某个表里的序号偏移**：`80, 88, 92, 96, 100, 104`。第 0 条是 80，之后每条 **+4**（第 1 条相对第 0 条是 +8，因为第 0 条占 8 字节）。
   即：`k = 0 → 80`；`k ≥ 1 → 84 + 4k`。
2. **`@242` = `256 − 名次`**：同一文件里从第二条起是 `255, 254, 253, 252, 251`（严格 −1）；第 0 条另算（`_TRK3` = 249 = 256−7，`_TRK4` = 248 = 256−8，即 `256 − (N+3)`，N = 音频轨数）。
3. **`@300`（连同 `@301`，u16 LE）= `156 + 6·N`**：N=4 → 180（`@301`=1，即 436）；N=5 → 186（442）。**每加一条音频轨 +6**。

而 `_TRK3` 里那条 `@300 = 117`、`@301 = 0` 的（id=46）是**异类**：它不是音频轨的自动化序列（`@234=100` 与第 4 条撞位），是「全局/主控」那一条，不跟这个规律。

### 21.2 这解释了 `_F7` 为什么崩
`_D14` 用的是模板（3 轨）的值，`N` 还是 3，而文件里已经有 4 条轨 → `@300` 少 6、`@242`/`@234` 全部错位一格。**照搬真实值（`_F7`）也错**，因为真实值是给「4 轨」算的，而我的文件结构和它不完全同构。正确做法是**按 N 重新算**，不是抄。

### 21.3 待确认的配套量

- `*Automation` 的 `qeSM` 条数 = 音频轨数 + 1（`_TRK3` 5 条 / `_TRK4` 6 条）。

**推论**：Stack 主行是**由 `ivnE:467` 通道 + `karT` 排列位置共同产生的**，
不像音频轨那样需要一条 `OCuA:201` 行头。这与「本工程里 `OCuA:201` 有 272 个
而实际轨道只有 6 条」一致 —— 那些 201 是**预分配的空行头池**，不是一一对应。

⇒ 新建 Stack 的最小增量可能是：**1 个 `ivnE:467` + 该行的 `karT:58` 成员**，
比新建音频轨少得多。下一步就在 `_STACK` 里克隆 SUM1 的 `ivnE:467`（同文件内、
改名字与 ID）做一次开箱验证。

### 32.6 负结果：只加 `ivnE:467` 不会产生 Stack 行
`_Z2.logicx` = `_STACK` + 克隆 `SUM1` 的 `ivnE:467`（名字改 `SUM2`、新 ID），
131,060 → 131,563 字节。离线 `channel_objects` 正确读出三条：
`SUM1 summing / SUM2 summing / FLD1 folder`。

开箱结果：`logic_list_tracks` **仍然 6 条**，没有 SUM2 行。

⇒ Stack 主行**必须有 `karT` 轨道条目**，`ivnE:467` 只是它的通道。
即一条 Stack 轨 = `karT`(带 `+2 = 0x14` 之类的层级标志) + `ivnE:467`，
而 `OCuA:201` 行头（音频轨那种 272 个的池子）不是它的组成部分。

下一步只剩一件事：把 `karT:58` 里属于 SUM1 的那一组成员一起克隆。
`_STACK` 里 `karT:58` 共 23 个、`+2 = 0x14` 的 9 个 —— 这 9 个是层级标志，
需要按名字/位置确认哪几个属于 SUM1。

### 32.7 `karT:58` 普查（`_STACK`，23 个；`karT` 合计 43 个）
`payload +2` 的分布（层级/类型标志）：

| `+2` | 个数 | idx |
|---|---|---|
| `00` | 13 | 428,432,433,434,435,436,438,439,440,450,451,454,462 |
| `01` | 1 | 437 |
| `14` | **9** | 444,445,446,447,448,449,452,453,455 |

`payload +40/+43` 只在 idx434–438 有非零值（`192/64`、`0/64`、`32/64`、`0/64`），
其余全 0 —— 这一组看起来是**轨道组末位标**那一族（与 `add_audio_track` 里
「`(32,64)` 末位标从模板移到新成员」对应）。

`_STACK` 实际 10 条轨（Audio 1–8 + SUM1 + FLD1），而 `karT:58` 有 23 个 ⇒
**每条约 2 个**，所以不能按「一个 karT = 一条轨」去找 SUM1。`+2=0x14` 的 9 个
更可能对应 9 条**音频**轨（Audio 1–8 + 一条隐藏/预分配），Stack 主行落在

**结论：只靠 `+2` 无法区分是哪几个 `karT` 属于 SUM1。**需要另找判据
（候选：`karT:58` 载荷里是否有指向 `ivnE:467` 名的引用、或 `+18/+40` 的组合）。

## §41 Waves 参数：能改「预设」，不能按名字改单个参数（实测结论）

### 实测（`Abbey Road RS124`，`aufx RS1M ksWV`）
`Waves_XPst` 解码后是纯文本 XML，`<PresetData Setup="SETUP_A">` 里 `<Parameters Type="RealWorld">` 是**一串扁平数字**：

- **429 个 token**（`*` 表示未设置），6 个预设逐个解码长度都是 429，其中 **39 个位置随预设变化**
- XML 元素只有 14 种：`PresetChunkXMLTree / Preset / PresetHeader / PluginName / PluginSubComp / PluginVersion / ActiveSetup / LoadMenuCategory / ReadOnly / VST24SideChainActive / PresetData / Parameters / PluginSpecificXMLData / …`
- **整个 XML 里只有 2 个 `name` 属性，都是预设名（`Full Reset`）**，没有任何参数名
- `PluginSpecificXMLData` 是空元素

⇒ **插件不吐「参数名 → 第几个数字」的对照表**，因此无法离线按名字写单个 Waves 参数。

### 为什么不能用 AU 参数反推
`au_dump --tsv --values` 每次都会**新建一个 AU 实例**再读值，与另一个进程里 load 的预设无关；实测 6 个预设下 63 个 AU 参数的值**完全不变**（变化参数数 = 0）。Waves 的 AU 参数对外也是只读的（`SetParameter` 返回 0 但回读不变）。

### 所以 Waves 的现实能力边界
| 能力 | 状态 |
|---|---|
| 读状态（`Waves_XPst`）| ✅ |
| **按预设编号/名字切换** | ✅ 实测：`--preset 7` 让 blob 6053 → 5769 字节；`--preset 0..5` 各自产出不同 blob |
| 按名字改单个参数 | ❌ 缺对照表；要补只能靠「一次只动一个控件」的人工样本，成本 = 控件数 × 一次保存 |
| 按位置改（知道 index 即可） | 🟡 技术上可行（改第 N 个数字），但**没有可信的 index 来源** |

**结论**：Waves 走「预设级控制」，通过 L2（`classinfo.class_info(..., preset=N)`）取得合法 blob 再拼进 `.cst`；不做单参数写入。这与文档里「L1/L2/L3 三层兜底」的表述一致，不需要改口径。

## 48.1 `vEuA:52` 只变了一个 4 字节字段

```
AUTO  : 00 00 00 5a | 00 00 00 00 | 00 00 00 7f | 00 00 00 5a | 00 00 00 00 | d2 00 00 00 | ...
AUTO2 : 00 00 00 5a | 00 00 00 00 | 00 00 00 7f | 00 00 00 5a | 00 00 00 00 | f0 00 00 00 | ...
                                                                             ↑ +20
```

`+20` = `0xd2` (210) → `0xf0` (240)，**+30**；其余 51 字节完全相同。
载荷 `+3` / `+15` / `+51` 三处仍是音量字节 `0x5a`（0 dB，与推子同一张表）。

## 48.2 曲线块的差异是「整段重算」，不是几个数值

差异偏移呈 **16 字节步长**（`+18/19/20`、`+34/35/36`、`+50/51/52`…），且总量 **9,697 字节**，
同时块长度从 **24,608 缩到 23,728（−880）**。

⇒ 该块不是「4 个控制点 × 16 字节」的列表，而是**按节拍/时间采样的密集包络**（或分段压缩表示）。
改变 4 个点的值会让整段重新采样 → 长度也会变。

## §62 纯离线新建 MIDI 区域 —— **打通（`_MR14` 实测 5 区域）**

### 62.1 真正的缺口：区域注册表容器（`qSvE`，本文件 serial=9）
不是 `gnoS`、不是 `OgnS`、不是 `MneG`、不是插入位置。区域能不能显示，由这个容器决定：

## 附表 A-9 · marker 新增：本轮三条硬结论（仍未打通）

用 `_M0`(6 marker) 与 `_M1`(7 marker) 这对**同谱系单变量阶梯**（Logic 亲手做的 6→7），
把「加一个 marker 到底要多什么」逼到只剩两处：

| 块 | `_M0` | `_M1` | 说明 |
|---|---|---|---|
| `qSvE` 容器 | 304 | **352** | `(len-16)/48` 由 6 变 7，即 +48 一条记录 |
| `qSxT` 名字对象 | 1 个 480 | **2 个 480** | 追加一个**长度 480** 的名字对象 |

**除此之外零差异**（`gnoS`、`MroC`、`ivnE`、`karT`、块数 463→464 全部不变）。

1. **`gnoS` 与 marker 数量无关 —— 现在有干净证明**：`_M0.gnoS` 与 `_M1.gnoS` 都是
   22,758 字节且**逐字节相同**，而两者 marker 数 6 ≠ 7。之前用 md5 闭合得到的
   同向结论，这次是直接对照，可以定案。

2. **克隆 483 长度的名字对象**（`_P7` 的最后一个）→ 文件**能打开**，Logic 仍只读
   **7** 条（`_MK1`）。结构上 `_MK1` 与 `_P7` 的差恰好就是上面两处（`qSvE` 352→400、
   多一个 `qSxT`），与 Logic 自己的 6→7 增量**同形**，但计数不增。

3. **克隆 480 长度的名字对象**（`_M1` 的最后一个，即 Logic 亲笔新加的那个）→
   文件**打不开**，Logic 退回「Choose a Project」对话框（`_MK2`）。

**判断**：名字对象的 480/483 不是「长度随便」，它内部 `+0` 与 `+20` 两处长度字段、
以及 `+27` 处的标志字节（`_M1` 的老名字是 `01`、新名字是 `00`）共同决定它是否被
计入；盲目克隆会把文件写坏。要真正打通，仍需读代码确认「计数从哪儿来」，
见 `CORE.md` 的能力矩阵（marker 新增标 🟡）。

**容器定位修正（已落库）**：`qSvE` 里 marker 容器的判据必须是
`payload[0] == 0x12` + `(len-16) % 48 == 0` + 尾部 8 字节 `f1 00 00 00 ff ff ff 3f`。
只凭后两条会命中 13 个候选（空容器也满足），旧的 `find_marker_chunk` 因此取错过。

### A-9 补充：三次克隆的实测结果（这一节把问题定性了）

以「每块 UUID 掩码后的 md5」逐块比对 `_M0`(6) 与 `_M1`(7)，结果是**无可争辩**的：

```
replace  qSvE 304 → qSvE 352
insert   + qSxT 480
其余 462 个块的内容 md5 完全相同（count=0）
```

也就是说 Logic 自己「加一个 marker」的全部动作就是这两处。但按同样动作生成的三份文件：

| 副本 | 基底 | 追加的名字对象 | Logic 读回 |
|---|---|---|---|
| `_MK1` | `_P7`（7 条） | 483 | **7**（不增） |
| `_MK2` | `_M1`（7 条） | 480（Logic 亲笔那个） | **打不开** |
| `_MK3` | `_M1`（7 条） | 483 | **6**（反而少一条） |

**结论**：名字对象不是「长度固定、随便克隆」的东西。同样追加一个 483，在 `_P7` 上计数不变、
在 `_M1` 上计数**减少**。这说明 Logic 是按**名字对象的内容**去和记录配对/去重的
（克隆出的名字文本与已有名字重复，会被合并或丢弃），而不是按数量对。

因此 marker 新增**不能靠离线克隆**解决，必须读代码确认「记录 ↔ 名字」的配对规则。
在此之前的正确做法是用运行时接口：`logic_markers create`（已验证可用）。

### A-9 再补：名字对象**不是按位置配对的**（新证据，定性完成）

把 `_M1`（7 条）末尾追加「一条记录 + 一个名字对象」后实测：

| 副本 | 追加的名字对象 | Logic 读回 | 关键现象 |
|---|---|---|---|
| `_MK3` | 483（`Marker ##` 模板文本） | 6 | 掉一条 |
| `_MK4` | 479（克隆 `Intro`，文本改成 `Outro`） | 6 | **bar 2 被改名为 `Outro`** |
| `_MK5` | 与 `_MK4` 相同，但显式插在**最后一个 RTF 名字对象之后** | 6 | **同样 bar 2 变成 `Outro`** |

`_MK4` 与 `_MK5` 的插入位置在文件里是同一处（名字块本来就在文件末尾，索引 457–463，
其后即文件结尾），结果完全一致，所以**不是插入位置的问题**。

结论（三条）：

1. **名字对象带身份，不是按顺序配对的。** 克隆一个名字对象会让它「抢」到第 1 条
   marker 的名字（bar 2 从 `Intro` 变成 `Outro`），而**最后一条 marke r 直接消失**
   （bar 30 不见了）。
2. 这正是「追加记录 + 追加名字」计数不涨、甚至变少的机制：新增记录拿不到合法名字身份，
   而克隆体又和原对象撞身份，导致 Logic 认为名字数少于记录数，按 `min(记录, 名字)` 截断。
3. 名字对象的 `Marker ##` 文本是**自动编号占位符**（显示时替换成 `Marker N`），
   所以多个 483 对象的文本字面完全相同——这也是为什么先前误以为「文本重复会被去重」。

**遗留**：名字对象的身份字段还没定位。它在载荷前 28 字节之外（`+0`/`+20` 是长度，
`+16` = 98 是 RTF 起始偏移，`+24`/`+27` 是标志），也未出现在 `qSxT` 块头 `+14`
（全部 65535）。要继续只能读代码。

**可用替代路径**：`logic_markers create`（运行时），已验证。

### A-9 结尾：`+8` 也不是名字对象的配对身份

`qSxT` 块头 `+8`（`/0x40000` 后为序）实测：

```
_M0（6 条）: 0, 4, 8, c, 10, 14, 18           ← 6 个名字
_M1（7 条）: 0, 4, 8, c, 10, 14, 18, 18       ← 7 个名字，末尾两个同值
```

按「新名字取 `max + 0x40000` = `0x1c0000`」生成 `_MK6`，结果**文件打不开**（退回
「Choose a Project」）。所以 `+8` 既不是可递增的配对序号，也不能随意改。

**至此 marker 新增的离线路径全部关闭**（容器判据、记录克隆、名字克隆、名字 `+8` 四条
都试过）。要打通只有读代码一条路；在此之前请用 `logic_markers create`。
